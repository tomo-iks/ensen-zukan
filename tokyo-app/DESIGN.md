# 設計・技術方針: (仮称) 東京街歩きアプリ

> 原則: 単純さを最優先する。要件を満たす最小の構成を選ぶ。

## 技術
- プラットフォーム: Webブラウザ(スマホ・PC両対応)
- 言語・フレームワーク: HTML + JavaScript(ビルドなし)
- データ保存: ブラウザ内。記録は IndexedDB(写真は容量が大きいため)
- 街データ: 同梱の JSON ファイル(読み取り専用)
- 公開: 静的ホスティング(サーバー・アカウントなし)
- 依存関係: 外部ライブラリは原則使わない

## データ設計(案)
元データのExcelから、1回だけ変換して `stations.json` を作る(アプリのビルドではなく、データ準備の作業)。

- **駅(読み取り専用、同梱)**: `id`(駅番号)、`name`、`reading`、`ward`(区市)、`category`(雰囲気タイプ)、`lines`(所属路線: 山手線 / 中央線快速)、`summary`(街の特徴・一言)、`moodTags`(気分タグ)
  - 新宿・東京・神田は両路線にまたがるため、`lines` を複数持たせる(駅は1件として扱う)
- **記録(利用者のデータ、IndexedDB)**: `stationId`、`visitedAt`、`photos`(端末内のみ)、`memo`
- **訪問済み**は、記録の有無から導く(別に持たない)

## 画面(案。Must 機能から導いたもの)
1. 沿線別の駅一覧: 訪問済み/未訪問を区別(F2)
2. 記録の入力: 駅を選び、写真とメモを保存(F1)
3. 記録の詳細: 保存内容の再表示(F1)
- 街の特徴の表示場所は未決定(REQUIREMENTS.md の未解決を参照)

## 容量・性能
- 利用者の写真は縮小して保存する(容量超過の予防)
- 外部由来の参考写真(元データでは9駅分で約28MB)は、最初のリリースには含めない。含める場合は駅ごとに遅延読み込みする

## 一貫性ルール
- 同じ概念には同じ名前・同じ文言・同じ見た目を使う(例: 「記録」「街」「沿線」)
- 新しい部品を作る前に、既存の部品を再利用できないか確認する
- 1ファイル/1関数は1つの責務に絞る

## エラー方針(提案・要確認)
- 保存に失敗した場合(容量超過・ブラウザの設定など)は、原因と次の行動を表示し、入力内容は消さない
- 写真・街データの読み込みに失敗しても、画面全体を止めない。該当箇所に理由を表示する
- ユーザー入力は保存前に検証する

## 確認方法(提案・要確認)
- Must機能ごとに受け入れ基準を手動で確認する
- 記録5分以内は、実際に計って確認する
- スマホとPCの両方で動作確認する
- 同梱の街データは、事実の誤りがないか人が目で確認してから確定する

## UI・命名規約
- 未設定(アプリ名・文言のトーンは後で決める。仮称のまま進める)

## v25 デザイン統一(index.html の CSS 末尾「デザイン統一」の章)
- 角丸: 小6 / 標準10(--r) / 大16(--r-l) / 丸999。ダイアログ・パネル・ポップアップは大16、ボタン・入力は標準10
- 文字: 11 / 12 / 13(本文) / 14 / 16 / 20 / 24。9〜10pxは11pxに、15は14に、17は16に、21は20に寄せた(地図上の駅名などは対象外)
- ボタン: 主=accent塗り(.primary)、副=枠線(.ghost)、選択=chip。押す部分は最低44px(chipは36px)
- 影・背景・文字色は var(--shadow) / var(--panel) / var(--ink)。ライト・ダークとも同じ変数で切り替わる
- 確認が要る操作(テーマ切替など)は、同じ確認ダイアログ(askOk)を使う
